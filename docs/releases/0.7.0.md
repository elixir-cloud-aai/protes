proTES can now account the resources that the tasks of each user used and
export them as Tool Execution Reports of ELIXIR Compute (format 0.0.2),
without personal data, and request an access token of its own for each TES
instance, all opt-in. The worker of the Helm chart gets readiness and
liveness probes by default, which changes upgrades of the chart: read the
[upgrade
steps](https://protes.readthedocs.io/en/v0.7.0/upgrading/#to-version-070)
first. This release was tested against Funnel 0.12.3 (TES 1.1, by label and
from its service info), TESP-API 0.2.0 with Pulsar 0.14.16 (TES 1.0) and
tesk-api 1.1.0 with the taskmaster and filer v0.10.6 (TES 1.0) in CI;
tesk-api 2.0.0 (TES 1.1) was not tested. See the
[documentation](https://protes.readthedocs.io/en/v0.7.0/) for details.

## Breaking changes

- The worker of the Helm chart has a readiness and a liveness probe by
  default (`celery inspect ping` through the broker): upgrades wait until the
  new worker answers, a worker that doesn't answer for 10 minutes is
  restarted, and values that set `worker.readinessProbe` or
  `worker.livenessProbe` are merged into the new probes; brokers without
  Celery's remote control (e.g., Amazon SQS) need both set to `null` (see the
  [upgrade
  steps](https://protes.readthedocs.io/en/v0.7.0/upgrading/#to-version-070))
  (#504, #505)

## Features

- Opt-in accounting of resource usage per user
  (`custom.accounting.enabled`): the Celery workers record the run time and
  the requested resources of each task that finishes at its TES instance, and
  admins get the totals per user at `GET /usage` (rule `admins-get-usage`)
  (#459, #490)
- Execution reports: admins get the usage records as Tool Execution Reports
  of ELIXIR Compute, format version 0.0.2, at `GET /usage/reports` (rule
  `admins-get-usage-reports`), for completed tasks of images in trusted
  namespaces, with the providers and locations of
  `custom.accounting.reports`; reports hold no user identifiers and no
  details of tasks (#502, #503)
- Opt-in access tokens per TES instance:
  `custom.tes.client_credentials.audience_parameter` (`resource` or
  `audience`) requests a token for each TES instance, for its `audience` or
  else its URL, so that TES instances can't use their tokens at each other
  (#397, #488)

## Security

- The image has dnspython 2.9.2, which fixes CVE-2026-128089 (high) of
  dnspython 2.9.1 in the image of 0.6.0 (#491)
- Lint rules find disabled TLS verification also in calls on sessions,
  decoding of JSON Web Tokens with unsafe algorithms and unsafe YAML loads;
  they find nothing in the code (#500, #499)

- The integration tests run on Funnel 0.12.3, check the TES 1.0 and 1.1
  paths on real TES instances, read Funnel's TES version from its service
  info, and share their helpers; the gate `CI passed` needs the job
  `Integration` (#479, #478; #481, #485; #486, #487; #480, #482; #425, #489)
- Checks of a deployment (`tests/smoke/deployment.sh`, and
  `tests/integration/check.sh` with a token) (#424, #474)
- The release workflow stops re-runs of a published release before they
  sign or tag a new image, the pin check also rejects packages from other
  sources than PyPI, and release notes may not hold relative links
  (#506, #507; #475, #476)
- The release workflow has a dry run: pull requests that change the release
  workflow, its scripts or the release metadata, and manual runs, run the
  whole release with an image in a registry on the runner and a draft GitHub
  release that is deleted afterwards, without publishing, signing or entering
  the `release` environment; signing moved to its own job for tag pushes
  only (#512, #513)
- Dependabot labels all its pull requests `type: dependencies`, and pull
  request runs of CI are cancelled only by new commits (#492, #493; #473)
