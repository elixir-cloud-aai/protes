proTES can now authenticate at TES instances with an API key (`auth:
api_key`), for TES instances that accept no access tokens of proTES, such as
Poiesis. The mode is opt-in and transitional, until proTES exchanges the
tokens of its users for tokens of each TES instance; existing configurations
work as before, so upgrades need no changes (see the [upgrade
notes](https://protes.readthedocs.io/en/v0.8.0/upgrading/#to-version-080)).
This release was tested against Funnel 0.12.3 (TES 1.1, by label and from
its service info), TESP-API 0.2.0 with Pulsar 0.14.16 (TES 1.0) and
tesk-api 1.1.0 with the taskmaster and filer v0.10.6 (TES 1.0) in CI;
tesk-api 2.0.0 (TES 1.1) and Poiesis were not tested (CI checks the API
keys against a stand-in TES instance only). See the
[documentation](https://protes.readthedocs.io/en/v0.8.0/) for details.

## Features

- API keys for TES instances: an entry of `custom.tes.backends` with `auth:
  api_key` sends proTES' key at that TES instance, from the environment
  variable `api_key.key_env` (or the file named in `<key_env>_FILE`), as
  `Authorization: Bearer <key>` or in another header (`api_key.header`), for
  every request to it, also by the Celery worker; the app and the worker
  refuse to start without a usable key, keys never appear in the config,
  the logs, the database or plugins, and redirects to other hosts drop
  them. Configured TES instances only (not those of a service registry);
  the TES instance sees all tasks of proTES as tasks of the key's account
  (see [API keys of TES
  instances](https://protes.readthedocs.io/en/v0.8.0/access-control/#api-keys-of-tes-instances)).
  The Helm chart takes `apiKey.keyEnv` and `apiKey.header` in `tes.backends`
  (#529, #530)
